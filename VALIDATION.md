# Compatibility and validation

Path Of Sight is an early Windows x64 release. Its automated checks cover map data, landmark handling, pathfinding, settings, local API protections, and terminal layout. A live Path of Exile 2 client has been used to verify terrain reading, nearby landmarks, routing to a checkpoint, and the Tab-map overlay in one campaign area.

Compatibility across game versions, zones, display scales, and all landmark types is not yet established. An update to Path of Exile 2 may require changes to memory signatures or offsets. Geometric landmarks are approximate until confirmed by a game object.

The repository includes an anonymized terrain fixture at `tests/pathofsight.Tests/fixtures/scorched-entry.json` for pathfinding checks. It contains terrain cells and relative positions, without account, character, or process-address data.

2026-09-26: A live Digsite waystone instance (`MapExcavation`) exposed a `BossArena_Forge_PCR_01` terrain tile. The updated landmark scan found one in-bounds «Арена босса» marker before any boss entity was available. The route planner returned no route to its tile centroid from the observed player position. Automated checks cover unique-boss classification, death/friendly filtering, transient boss markers, and arena-tile selection. A live boss fight and other waystone map layouts have not yet been checked.

Follow-up: a screenshot showed that this terrain marker was visibly outside the arena. Read-only inspection of a fresh Digsite instance found a sleeping `BossLeagueContentMarkerMain` entity with a position at grid ~752.5,1743.5 before the boss appeared. In Clearfell, a sleeping `BossRoomMinimapIcon` position (~1150.5,789.5) was close to the known boss terrain landmark (~1138.5,782), supporting the position field interpretation. The app now prefers these preloaded markers in waystone maps. Visual alignment of the rebuilt app in a live Digsite instance remains to be confirmed.

Automatic routing selects a destination only in `Map…` areas. It prefers a preloaded map-boss spawn marker and otherwise uses a recognized boss-arena tile; a living Unique entity is never an automatic target, because Rogue Exiles and Ritual bosses also have that rarity. Manual selection can temporarily override the route. Automated checks cover the map-only gate and target priority. A complete automatic route from the entrance to a Digsite boss has not yet been observed live; disconnected terrain still yields an honest no-path status.

Long-distance routing regression: on a connected 800×800 synthetic map with a distant opening in a wall, the former 250,000-node limit found a route only near the boss; the new map-boss budget finds the route from the entrance. Campaign boss searches retain the old budget. A read-only check in a live `MapWillow` instance found a preloaded boss marker and a nine-point route from the observed player position in 65 ms with the old limit; this map did not reproduce the delayed-route issue. The affected layouts still need a live entrance capture to distinguish search exhaustion from disconnected terrain or a boss marker that appears only nearby.

Unique-target regression: synthetic map POIs now confirm that a Rogue Exile or Ritual boss cannot start or steal the automatic route, even after spawning while the map-boss marker exists. A generic boss-labelled stair tile also cannot become the automatic target. These checks do not prove that every map exposes a completion-boss marker; layouts without one require further live inspection.


Profile/settings implementation: automated checks cover all six defaults, independent persistence, reset-current, legacy backup/migration, invalid profile input, failed-write preservation, temporary filter precedence/reset, stale profile/instance/revision rejection, the three routing modes, hidden targets, route invalidation, metadata classification, NPC transience, chest completion state, and scrolling TUI menus at narrow/small dimensions. Existing pathfinding and map-only boss-selection checks remain enabled.

Initial profile-release demo verification (before Normal/Magic/Rare support): a running simulated client was controlled through the TUI input path; choosing Act Rush changed the browser profile and disabled route selection. Browser interaction confirmed temporary Shrine hiding (7 targets → 6), restoring profile filters (6 → 7), grouped filters, and disabled Normal/Magic/Rare controls. The demo uses synthetic data and does not read the game.

Live gaps: no new live-client validation was performed for NPC/chest scanning or the mechanic namespace rules. Strongbox/Azmeri rules are explicitly marked unverified in the filter catalogue. Other mechanics, quest variants, trials and Incursion also require live coverage; unknown metadata is kept as Other POI. The name database contains mixed upstream content and is not treated as proof that a mechanic is available or fully supported in the running PoE2 version.

TUI column/input follow-up: Settings and Profiles reuse the main frame's right column at widths of at least 65 columns and heights of at least 18 rows. Checks cover unchanged left-column content, scrolling to the final mechanic, frame bounds, and compact fallback. The production input-loop regression consumed six queued events in 1403 ms before the fix and under 1 ms afterward on this machine. This measures dispatch/render callbacks, not physical keyboard or terminal latency. Idle polling is 10 ms; frame checks run every 200 ms, but unchanged rows emit no writes. A full non-clearing overwrite every two seconds repairs unobserved terminal resize round-trips. No settings persistence is deferred.

TUI flicker/style follow-up: enabled settings use checkmarks, profile headings explicitly say Profile, normal menu text is gray and selection is bright white. ANSI regression checks reject erase-before-paint sequences, verify unchanged-frame suppression and trailing-space cleanup, and keep border/left-column font weight independent of the selected item. The old renderer erased every row before repainting and applied selection bold to borders. Those causes are removed; physical display flicker in the user's terminal is not directly measured by these checks.


Earlier monster-rarity release (superseded): automated checks covered Normal/Magic/Rare conversion and a 10-POI demo. That release did not read sleeping monsters.

Current distant-monster check: a read-only probe of one live PoE2 area resolved the terrain and entity lists, found one awake Rare and four sleeping Magic monsters with readable rarity and positions. The sleeping scan took 65–70 ms and about 40,793 process reads in this area; the app scans every two seconds. This verifies that at least some distant monsters are available in client memory. It does not establish whole-map coverage, or live death/despawn and dense-area performance. Synthetic checks verify Normal exclusion, Magic disabled by default in every profile, Rare enabled in Default/Custom, version-2 profile migration with backup, TUI controls, browser categories, and the existing route/visibility regressions. The demo now has Magic and Rare markers (9 POI total). The restricted reader still skips loot/mod/item-identity reads.

Rare visibility follow-up (2026-09-27): a read-only probe sampled the same Digsite instance while the player moved across it. At the first point it found no Rare in either the awake or sleeping entity list. Later, without an instance/hash change, it found 1 awake and 19 sleeping Rare; after further movement it found 16 awake and no sleeping Rare. A separate live check on MapExcavation compared readable Rare IDs from both lists with the `MapService` snapshot and found 1 in memory, 1 in the radar, and 0 missing. These observations show that Rare entries become available in the client's entity lists during movement and that a readable Rare reaches the radar. They do not prove whether the server transmits the entities at that moment or the client activates data stored in some other structure. The terrain's full geometry is available before these entity entries appear.

Other POI availability follow-up (2026-09-27): a read-only probe of the current Digsite/MapExcavation instance found one map-boss terrain landmark more than 250 grid units from the player, available before a matching active entity. Ten samples of the same instance found no Shrine, Waypoint, Checkpoint, or mechanic in the curated tile landmarks, restricted awake POIs, or matching sleeping non-monster metadata. This map therefore verifies early availability of a static terrain landmark only; it cannot establish early or late availability of those other categories. The application currently reads ordinary non-monster POIs from awake entities and curated terrain paths, while its general sleeping-entity scan is limited to monsters and boss spawn markers. A live map containing each relevant POI is needed to distinguish absent client data from a missed sleeping POI or an uncurated terrain tile.

Later in the same Digsite instance, a raw read found three `RitualRuneObject` entities in `AwakeEntities` with valid grid positions at widely separated locations, one `Shrine` in `SleepingEntities` with a valid grid position, and an awake checkpoint. The restricted POI reader returned the checkpoint but skipped all three ritual rune objects because they had no minimap icon; the app does not scan sleeping non-monster POIs, so it also missed that Shrine. This proves that at least some distant Ritual/Shrine positions are already present in client memory and that their absence from the radar is an implementation gap. Three rune objects do not prove three distinct Ritual sites. No recognizable Vaal/Incursion path was found in the current terrain tiles or awake/sleeping entity metadata, so early visibility of the Vaal encounter remains unverified.

Unmoved-at-entrance MapMarrow check (2026-09-27): in the same instance and at the same player coordinates across repeated samples, a raw terrain/entity scan found an awake checkpoint, three `Expedition2Encounter` entities about 391–451 grid units away, three `RitualRuneObject` entities about 487–1342 units away, nine sleeping Expedition markers, and an `Incursion/Tiles/Features/Waygates/WaygateDeviceMaraketh2` terrain tile. The restricted reader returned the checkpoint and Expedition entities but omitted all three Ritual rune objects because they lacked minimap icons. No Breach or Essence path appeared in the terrain tile list or awake/sleeping entity metadata. Numerous `Abyss` terrain paths describe the map's generic cave floors and walls; they do not identify an encounter location. Thus some mechanism positions are available across the map at entry, but this sample cannot supply positions for every known encounter, and the `WaygateDeviceMaraketh2` tile is not by itself proof of the user-facing Temple marker. This is an observation of the inspected client structures, not proof that no other game structure encodes the missing positions.

Reader fix (2026-09-27): the restricted reader now accepts `RitualRuneObject` without a minimap icon, and its existing sleeping-map pass includes a small whitelist of stationary POIs with readable positions. `Expedition2Encounter` now uses the Expedition category. In a live MapMarrow snapshot after this change, the radar contained three Ritual rune objects, three Expedition2 encounters, and one checkpoint. The map contained no Shrine for a live check of the sleeping-Shrine path; that path is covered synthetically. Breach, Essence, Abyss encounter, and Temple-marker positions remain unverified or unavailable from the inspected structures. The 303-check Release harness passes.

Code reduction (2026-09-27): removed unused upstream full-entity loot/mod/item readers, player vitals, ritual-shop/hover/health-bar/camera/monolith helpers, and AOB research helpers. Both app and probe call the POI-only `Entities` path; map UI visibility, monster HP/rarity, landmarks, terrain, and GameState signature scanning remain. Release build and 303 harness checks pass. The cleanup was not separately verified in a live game client.

Azmerian Ranges follow-up (2026-09-27): a read-only live probe found a 2968×5727 walkable grid (16,997,736 cells). The previous 16,000,000-cell validation cap rejected it despite a consistent 1,484-byte row stride and zero failed process reads. With the cap raised to 32,000,000 cells, the probe decoded the terrain and a fresh `MapService` published a ready Azmerian Ranges snapshot with a terrain image. The live snapshot had three Expedition POIs, all `Expedition2Encounter` rune stations; the three `ExplodingFill_StrongBox` objects observed in the same area are now excluded from map POIs. No Expedition camp/tent marker was identified in the inspected awake or sleeping metadata, so none is synthesized. This confirms the map and POI filtering in that instance, not every layout or game version.

Rare death follow-up (2026-09-27): after a live kill, a read-only sample found multiple awake Rare corpses with current HP 0 and positive maximum HP. The old reader discarded those entries before the map service could reconcile IDs with its two-second sleeping snapshot. The reader now exposes dead IDs for reconciliation, and a per-instance tombstone prevents a stale sleeping Rare from reappearing. Synthetic checks cover stale-snapshot suppression and instance reset. A 40-second live snapshot watch during another kill showed Rare marker changes, but did not identify the killed monster's ID; continuous before/after confirmation for that specific monster remains open. The Release harness passes 314 checks, and rendered demo views confirm Rare has no overlay or browser-map text and the boss arena reads `BO$$`.

Mechanic completion follow-up (2026-09-27): the live Azmerian Ranges snapshot identified `Metadata/MiscellaneousObjects/Brequel/BrequelInitiator` as the hand reported under Other POI. It is now classified as Breach and labelled `Breach`. One completed `RitualRuneInteractable` and an unfinished `RitualRuneObject` shared the same grid position, while two other Ritual sites were far away. The POI tracker now keeps completion within the current instance and removes completed mechanics plus same-category POIs within 23 grid units; synthetic checks cover one-site Ritual removal, transient incomplete reads, other mechanics, and instance reset. A fresh live reader confirmed the Breach name/category and intact map, but it started after the Ritual completion marker had left the awake list, so that finished Ritual site remained visible. Breach uses a separate completion flag: in a live Lost Towers instance, hand ID 104 had `MinimapIcon +0x38 == 0` before opening and while active, then `1` after closing. The ordinary `CompletedState` remained zero. Two other hands in the same instance still had `+0x38 == 0`. The updated reader uses this flag only for `BrequelInitiator`; a fresh live map-service snapshot removed ID 104 while keeping the other two Breach hands. Other Breach variants and mechanics still need live completion checks.

Shrine completion follow-up (2026-09-27): in a live Canyon instance, Shrine ID 641 (`Metadata/Shrines/Shrine`) remained awake after the player took its buff. Its `MinimapIcon.CompletedState` stayed zero, while `Shrine +0x24` changed from 0 to 1 and remained 1. The reader now treats that Shrine component value as completion, with a failed read retaining the marker. A fresh live reader reported ID 641 completed, and a fresh map-service snapshot had no Shrine target while preserving other map POIs. The console harness checks that completing one Shrine hides it without hiding a separate Shrine, and that it stays hidden until the instance resets. Other Shrine metadata variants have not been sampled live.
